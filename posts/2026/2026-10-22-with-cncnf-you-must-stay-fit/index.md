# With CNCF you must stay fit and be ready evolve

All **cloud native** projects, including Kubernetes are fast-growing. Fast growing mean not just adding new feature but forcing you to stop using old features. If you know shat [major semantic version increase](../../2021/2021-12-21-semantic-versioning/index.md) you will undersantand what I mean - it means breaking changes, my friends, breaking changes is normal in fast-growing.

I'm using Azure since 2011 but last couple years ago I discovered [CLOUD NATIVE COMPUTATION FOUNDATION aka CNCF](https://www.cncf.io/) with such frameworks as Kubernetes and [DAPR](https://dapr.io/). We started with simple: [Azure Container App aka ACA](https://learn.microsoft.com/en-us/azure/container-apps/overview) was fast way to develop containerized microservices.

I'm working on the transformation of the largest CI/CD pipelines service at Microsoft, which supports 100K pipelines. The service runs 100K builds per day and 20K releases per day, and it consumes 800K+ VMs and container agents per day, impacting 50,000 developers at Microsoft. For this solution it was critical to run on funcamental Azure Ring 0 platform as [Azure Kubernetes Services aka AKS](https://learn.microsoft.com/en-us/azure/aks/what-is-aks).

1.5 years ago I have created first real Kubernetes experemental AKS cluster and naive expectations to leverage unlimited power cloud-native ecosystem eventually become thrive to be secure and compliant specailly for high demanding Microsoft Azure 1P standards.

When I start learning in brand new domain area form me, something I knew that there is one instrument that was guarantee giving me at least 30% of expertise - this instrument is called "a book". To learn Kubernetes I decided to read book written by one of creators of Kubernetes Brendan Burns. When I write this article Brendan is taking position of TF/CVP Azure Cloud Native & Mgmt in Microsoft Azure. [Kubernetes: Up and Running: Dive into the Future of Infrastructure](https://www.amazon.com/dp/109811020X?lv=shuf&channelId=520&plpRedirect=mhFallback) is great book, but what I didn't know is that it is just 300+ pages introduction to big k8s ecosystem.

If somebody came to reading this post alreayd convinced that Kuberentes is [The Tyranny of the Unnecessary](https://www.linkedin.com/pulse/tyranny-unnecessary-how-kubernetes-empowers-incompetent-gary-yang-aci7e/) then I'm happy that you are happy "citizen developer" being hosted on Azure Funcitons or Amazon Lambda. Kubernetes is the jorney that you will enter and exit a different personality.

On Azure Antares-family PaaS (e.g. AppService, AzureFunction, Azure Container App) when you create service you automatically get DNS name like `https://myservice.azurewebsites.net`.
When you use Kubernetes, your service create [ingress](https://kubernetes.io/docs/concepts/services-networking/ingress/) where rabbit hole begins. I just will enumerate changes that had to make on our test and prod kubenretes clusters realted to `ingress`.

WARNING: while this list enumerates all ingress combinations that I used in production, text contains sarcasm and irony realted to my fillings that I was filling when had to change technology.
1. First Impression *Ingress*. You read [Kubernetes book](https://www.amazon.com/dp/109811020X?lv=shuf&channelId=520&plpRedirect=mhFallback) exited learning how flexible Kubernetes system is.
2. You fill the power of k8s and go create [Instio Service Mesh](https://istio.io/latest/about/service-mesh/). Exitement is turning into frustration when you see [400-700 pages books about Istio](https://www.amazon.com/Istio-Running-Service-Connect-Control-ebook/dp/B07YGRPDC1/ref=sr_1_6?crid=2ZJZDT5PZ9BJ7&dib=eyJ2IjoiMSJ9.Z-nDJbbLZFh33bGKZ9Ykeosk-YQXLnl6J--MiKvnTbgfiN1dn-GhLK-uvv19g-05iQaCANSUbdsflY297obTSUSoU4Rb-EHc5PexBrucCWX-ugRU2Od1XLCpF65_E7wpJRy90N4SBDwQZsqmTLwbiHc48TuB0B4R7UuQujkPSiu56-LsoGRNGGdKYvVNWseGlHrQ3YdA6eecYcQnQOh0xkoVcwzyezsYlravhd0M1MQ.DLoe1obCcTBQQ52DNf_jGxV4oK_6GVB2_YospvTX-0M&dib_tag=se&keywords=istio+service+mesh&qid=1792636012&s=digital-text&sprefix=istio+service+mes%2Cdigital-text%2C219&sr=1-6). You still can spend hours searching for somebody who will explain you how to make it 1P secure and compliant and in this moment you start looking for something simpler.
3. You want something simple like `nginx` / `ingress` like Kubernetes book was teaching you everything will be clear again.
4. `nginx` is dead and you must go to [Gateway API](https://kubernetes.io/docs/concepts/services-networking/gateway/) again, but this time it is different than old [Istio Gateway](https://istio.io/latest/docs/reference/config/networking/gateway/) but this is new refined [Gateway API](https://kubernetes.io/docs/concepts/services-networking/gateway/) that requires installing Istio again but only for `Gateway API` - so you still need to remember that under the cover it running Istio described in 700 pages book that you offcourse didn't read.
5. Your endpoitns are under hacker attack and you need another `Gateway API` called [Azure Application Gateway for Containers](https://learn.microsoft.com/en-us/azure/application-gateway/for-containers/overview) that also implement `Gateway API` protocol but are different internally: instead of being OSS like Istio, `Gateway for Containers` makes just slim adapter between ergonomic k8s `Gateway API` and powerful Microsoft enterprisy security solution.
6. You like k8s `Gateway API` but you looking simplicity again and finding it in [Application routing Gateway API](https://learn.microsoft.com/en-us/azure/aks/app-routing-gateway-api?pivots=azure-cli). You fill that finally you are safe, you use modern stable and easy enough technology, but networking experets are saying you that `Application routing Gateway API` is just little bit modernize version of deprecated `nginx` and another new option is upcomming. THE END

Now you may imagine fillings how you may become "overfeed" by cloud **cloud native** "fast-growing" rithm.

Solution: with CNCF you must stay fit and be ready evolve. If you still need powerful platform but don't need evolution: then go use [Service Fabric](../../2021/2021-06-30-from-service-fabric-to-app-service/index.md).
