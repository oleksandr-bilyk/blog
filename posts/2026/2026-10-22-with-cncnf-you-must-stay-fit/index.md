# With CNCF, you must stay fit and be ready to evolve

All **cloud-native** projects, including Kubernetes, evolve fast. That means not just adding new features but forcing you to stop using old ones. If you know what a [major semantic version increase](../../2021/2021-12-21-semantic-versioning/index.md) means, you understand what I'm talking about. Breaking changes, my friends. Breaking changes are normal in a fast-moving ecosystem.

I've been using Azure since 2011, but only in the last couple of years did I discover the [Cloud Native Computing Foundation, aka CNCF](https://www.cncf.io/), and projects like Kubernetes and [Dapr](https://dapr.io/). We started simple: [Azure Container Apps, aka ACA](https://learn.microsoft.com/en-us/azure/container-apps/overview), gave us a quick way to develop containerized microservices.

I'm working on the transformation of the largest CI/CD pipelines service at Microsoft, which supports 100K pipelines. The service runs 100K builds and 20K releases per day, and it consumes 800K+ VMs and container agents per day, impacting 50,000 developers at Microsoft. For this solution, it was critical to run on a foundational Azure Ring 0 platform like [Azure Kubernetes Service, aka AKS](https://learn.microsoft.com/en-us/azure/aks/what-is-aks).

A year and a half ago, I created my first real experimental AKS cluster. My naive expectations of tapping into the unlimited power of the cloud-native ecosystem eventually turned into a struggle to stay secure and compliant, especially under Microsoft's demanding Azure first-party (1P) standards.

When I start learning a completely new domain, I know there's one tool guaranteed to give me at least 30% of the expertise. That tool is called "a book". To learn Kubernetes, I decided to read a book co-authored by one of its creators, Brendan Burns. As I write this, Brendan holds the TF/CVP role for Azure Cloud Native & Management at Microsoft. [Kubernetes: Up and Running: Dive into the Future of Infrastructure](https://www.amazon.com/dp/109811020X?lv=shuf&channelId=520&plpRedirect=mhFallback) is a great book. What I didn't know was that its 300+ pages were just an introduction to the huge k8s ecosystem.

If you came to this post already convinced that Kubernetes is [The Tyranny of the Unnecessary](https://www.linkedin.com/pulse/tyranny-unnecessary-how-kubernetes-empowers-incompetent-gary-yang-aci7e/), then I'm happy you're a happy "citizen developer" with your app hosted on Azure Functions or AWS Lambda. Kubernetes is a journey. You come out a different person.

On Azure Antares-family PaaS offerings (e.g. App Service, Azure Functions, Azure Container Apps), creating a service automatically gives you a DNS name, such as `myservice.azurewebsites.net`.
When you use Kubernetes, you create an [Ingress](https://kubernetes.io/docs/concepts/services-networking/ingress/) to expose your service, and that's where the rabbit hole begins. Here's the list of ingress-related changes I had to make on our test and production Kubernetes clusters.

WARNING: These are all ingress combinations I've used in production. The sarcasm and irony reflect how I felt every time I had to change technologies.

1. First impression: *Ingress*. You read the [Kubernetes book](https://www.amazon.com/dp/109811020X?lv=shuf&channelId=520&plpRedirect=mhFallback), excited to learn how flexible Kubernetes is.
2. You feel the power of k8s and set up an [Istio service mesh](https://istio.io/latest/about/service-mesh/). Excitement turns into frustration when you see [400-700-page books about Istio](https://www.amazon.com/Istio-Running-Service-Connect-Control-ebook/dp/B07YGRPDC1/ref=sr_1_6?crid=2ZJZDT5PZ9BJ7&dib=eyJ2IjoiMSJ9.Z-nDJbbLZFh33bGKZ9Ykeosk-YQXLnl6J--MiKvnTbgfiN1dn-GhLK-uvv19g-05iQaCANSUbdsflY297obTSUSoU4Rb-EHc5PexBrucCWX-ugRU2Od1XLCpF65_E7wpJRy90N4SBDwQZsqmTLwbiHc48TuB0B4R7UuQujkPSiu56-LsoGRNGGdKYvVNWseGlHrQ3YdA6eecYcQnQOh0xkoVcwzyezsYlravhd0M1MQ.DLoe1obCcTBQQ52DNf_jGxV4oK_6GVB2_YospvTX-0M&dib_tag=se&keywords=istio+service+mesh&qid=1792636012&s=digital-text&sprefix=istio+service+mes%2Cdigital-text%2C219&sr=1-6). You can still spend hours looking for somebody to explain how to make it meet 1P security and compliance standards. At that point, you start looking for something simpler.
3. You want something simple, like `nginx` and Ingress, just as the Kubernetes book taught you. Everything will make sense again.
4. `nginx` is dead, and you have to move to [Gateway API](https://kubernetes.io/docs/concepts/services-networking/gateway/). Not the old [Istio Gateway](https://istio.io/latest/docs/reference/config/networking/gateway/), but the new, refined Gateway API. You end up installing Istio again, this time just for Gateway API. So you still need to remember that, under the hood, it's running Istio, described in that 700-page book you of course didn't read.
5. Your endpoints are under attack, and you need another Gateway API implementation: [Azure Application Gateway for Containers](https://learn.microsoft.com/en-us/azure/application-gateway/for-containers/overview). It implements the same Gateway API but works differently under the hood. Instead of an open-source solution like Istio, you get a slim adapter between the ergonomic k8s Gateway API and a powerful Microsoft enterprise security solution.
6. You like the k8s Gateway API, but you're looking for simplicity again. You find it in [Application routing Gateway API](https://learn.microsoft.com/en-us/azure/aks/app-routing-gateway-api?pivots=azure-cli). You finally feel safe: the technology is modern, stable, and simple enough. But networking experts tell you it's just a slightly modernized version of the deprecated `nginx`, and another new option is on the way. THE END.

Now you can imagine how it feels to be "overfed" by the pace of this **cloud-native** ecosystem.

Solution: with CNCF, you must stay fit and be ready to evolve. If you still need a powerful platform but don't need the evolution, go use [Service Fabric](../../2021/2021-06-30-from-service-fabric-to-app-service/index.md).
